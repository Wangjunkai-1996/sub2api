## 1. 已确认的业务决策

### 1.1 部署职责

`终端用户 → NewAPI → Sub2 → 上游模型账号`

- **NewAPI** 持有全部终端用户，负责对外接入、用户额度与收费。
- **Sub2** 是运营者管理的内部上游账号池和代理；当前部署只有运营者自己的管理账号。Sub2 源码已有的 User/API Key 框架实体不代表存在另一批终端客户。
- 重试、切号由 Sub2 实施；“切号”是切换上游账号，不是切换 NewAPI 用户。
- 不为本次恢复新建 Sub2 终端用户、钱包、租户管理或计费账本；保留既有框架鉴权和用量记录。
- 上游重复费用是运营者明确接受的恢复成本，不作为停止恢复的理由。NewAPI 收费仍由 NewAPI 的现有生命周期负责。

### 1.2 本轮明确选择

用户确认：

> 不管有没有输出、不管会不会导致上游重复计费，都要执行重试或切号流程，不能简单向用户抛错。
>
> 接受可见的重新生成，优先首字速度和最终完成。

据此锁定：

1. **保留真正流式输出。普通文本不等待整轮生成结束。**
2. **不恢复整段流式缓存，不以整轮暂存换取“透明重试”。**
3. 已经展示的失败片段允许保留，但必须明确标识其已中断；后面是独立的重新生成结果，不伪装成原段自然续写。
4. 是否已经输出、是否可能重复上游计费，均不得单独终止可恢复故障的恢复调度。
5. 接受可见重生成不等于授权重复执行外部工具动作，也不等于允许破坏 JSON/schema。

### 1.3 与旧决策的关系

[2026-10-13 四项退场方案](KKAI_REMOVE_SCHEDULER_ATOMIC_WARMUP_STATE_PLAN.md) §5.2 中“首段语义及时下发、移除整段原子缓存”的决定继续保留。本方案只改变其中“输出后失败即可结束并报错”的恢复行为。

不恢复 `OpenAIAtomicStreamFailover`、`GATEWAY_OPENAI_ATOMIC_STREAM_FAILOVER`、旧 `atomicStreamRetry/commitAtomicStream`，不恢复分组调度覆盖、暖机、主动 STATE 采集/注入等无关退场功能。之前对整段缓存的讨论已由用户的新选择取代，不是待实施方案。

## 4. 总体架构：恢复与交付分工

### 4.1 单一恢复 owner

Sub2 的协调层作出：`retry_same_account`、`switch_account`、`rebuild_continuation`、`wait_until_eligible`、`finish` 或 `stop`。

适配器只报告本次 attempt 的结果和健康/用量事实。逻辑流输出器决定公开什么：正常 delta、明确的重生成分段，或唯一的最终终态。适配器不得直接把可恢复的 `response.failed/error/[DONE]` 发出去后再宣布要重试。

NewAPI 对受管渠道从请求入口就知道恢复由 Sub2 负责。现有 `X-Sub2-Retry-Status: exhausted` 保留为兼容终态提示，但不能靠这个可能来不及发送的响应头独自承担 ownership。NewAPI 不为 Sub2 的中间失败重新发放一套调用预算。

NewAPI 受管传输采用从原请求入口起算的固定 930 秒上限，给 Sub2 900 秒逻辑预算之外保留至多 30 秒网络与终态交付空间；若客户端 context 更早截止则服从更早期限。HTTP client、响应头等待和 scanner 均遵守该绝对期限，收到数据、重试或切号不续期。用户取消直接传播到 Sub2，不能继续沿用普通请求首响应后的延迟 drain 策略。

### 4.2 状态与隔离

`进入 → 准入/选号 → 执行 → 正常增量交付 → 本次失败 → 分类/标记重生成 → 等待或重新准入 → 新 attempt → 最终结果`

- 下游连接 context、逻辑请求 context、单次 attempt context 分离。
- 每次真实调用重建 body reader、解析器、首输出计时和局部错误状态；逻辑 ID、总预算、已交付事件索引及执行记录不重置。
- 单轮超时不能被误判成客户端取消；失败轮释放上游连接和账号/出口 lease 后再等待。
- 不引入独立工作流平台，不并行复制同一请求去“抢赢家”；先复用现有 handler、调度器和 retry budget。

## 5. 对外保持真流式，并明确重新生成

### 5.1 普通 Responses 文本

- 对客户端维持一次逻辑 response 生命周期；第一段正常 delta 立即转发。
- 上游失败时扣住失败终态，先按已交付内容逐项闭合旧 text/refusal part 与 item。仅在已有可见业务内容时，另建独立 assistant message 承载明确的网关中断说明；说明不追加到旧 part，也不改写拒绝内容。尚无可见内容则静默恢复，不为前输出错误先发提示；不得重开或重复关闭已有 done 的层级。
- 说明文本例如：`【上次生成中断，正在重新生成；请以下方新结果为准。】`，使用合法 assistant message 承载，随后用新 answer item 流式输出新尝试。
- 后续上游 `response.created` 不是第二个对外 response；由有类型的映射维护 response/item ID、output/content index 与全局递增 sequence。
- 最终公开 output 必须反映已交付的旧片段、标记和新结果；不可在最终对象中假装旧片段从未发过。展示转录与可续接历史分别维护：前者含旧片段和提示，后者仅纳入最终有效轮的上下文；不从公开 output 整包误建恢复历史。
- 仅有一次最终 response 终态。不能把 HTTP 200、EOF、[DONE] 单独视为成功。
- 推荐以 `status=completed` 闭合旧展示 item，随后发送独立的中断说明 item；前者仅表示该展示段已收尾，内部模型 attempt 仍为 abandoned，整体 logical response 保持 in_progress。`incomplete` 作为比较兼容序列，不作为并列默认。推荐序列仍须通过目标客户端增量与最终聚合两种读取方式；schema 合法不等于客户端已验证。

这是一种**可见分段重生成**，不是撤回、无损替换或保证与旧文本一致的续写。是否有界保存已发送片段以构建最终对象，不得影响正常 delta 及时发送；它不是等待成功再交付的整段缓存。

### 5.2 普通 Chat 文本

保持一个 logical completion ID 和原 choice 关联。已有可见正文的 choice 在 content delta 中追加清楚的重启分隔，再流式输出新的完整答案；没有旧可见内容的 choice 不先发分隔。不能混入失败轮的 finish_reason、usage 或 [DONE]；只有最终成功或合法限额轮按支持的正常结束契约发送终态，最终失败走明确错误事件。所有 choice 的非空 finish_reason、结束 usage chunk 和 [DONE] 都扣留到整个 attempt 结果确定；失败轮全部丢弃。多 choice 按整轮协调恢复、逐 choice 标记旧段，不能只完成第一个 choice 就结束，也不能将不同轮的 choice 拼成一个成功结果。

### 5.3 内部控制与 NewAPI

恢复元数据必须通过双方明确支持的内部控制契约传递，并在 NewAPI 的文本累计、usage、工具统计及终态处理之前消费。仅加 SSE `event:restart` 不够：当前 NewAPI scanner 主要处理 data 行。

普通客户端能看见的提示必须是其格式支持的文本项；内部控制帧不冒充模型文本，也不未经协商泄露给外部 SDK。NewAPI 保持流打开，隔离失败轮的暂态 usage/工具统计；不把中间 failed 当逻辑失败。具体帧格式、能力门和降级语义由开发文档锁定。

首个业务提交前只暂存预算内的少量控制元数据，不因控制帧单独提前 Flush HTTP 头，以保留正常首轮上游响应头的传递机会。最终终态首次携带的正文须先正规化为同 attempt 的常规业务事件，再发布 terminal；受管模式禁止从含旧片段的复合最终 output 回填 winner 文本计量。

### 5.4 工具、reasoning 与结构输出

- 正文仍实时发送。所有客户端可执行工具事件（包括转换后的 `tool_search_call`）及参数在有界局部暂存中累积，直到本轮达到可接受终态，且 authoritative item/终态快照证明每个调用及参数完整，才提交完整调用批次；不能只等单个 tool item.done 就假定后续不会失败。合法限额终态并不授权执行截断的 arguments/custom tool input，必须保留真实 incomplete/length 语义。
- 失败轮的工具参数、call ID、密文 reasoning 不与新轮拼接。已执行外部动作依靠执行记录或幂等机制处理，重复费用授权不扩展为副作用授权。
- 密文 reasoning/compaction 的不透明单元局部扣留到本轮可接受终态；失败轮不公开、不进入后续历史，仅交付最终有效轮完整且归属正确的 item。可见 reasoning summary 按文本分段规则实时输出。不能通过修改 ID 或丢弃必要密文假装得到等价上下文。
- 严格 `json_object/json_schema` 禁止插入文字分隔。首期默认保留其协议：需要完整结构单元校验时只暂存该结构单元；提交条件同时要求结构完整、校验通过及本轮已到可接受终态，JSON 刚闭合不等于可以提交。明确一个 JSON 对象可能就是整份结构答案，会增加此类请求的首字延迟；限额结束导致结构不完整时不得伪造成 schema 成功。**这不是给普通文本恢复整段缓存。**
- 若要求严格结构也实时输出且能重启，只能使用明确协商的客户端 restart 能力；未验证前不能宣称支持无损重生。
- 工具/结构单元超限按明确的本地容量失败处理，不偷偷退回不安全的拼接或无界内存。

### 5.5 非流请求与交付断开

stream=false 始终返回普通 JSON，可以内部流式读取并恢复，但不发 SSE 心跳或提前 200 空白。已有结果向下游发送时发生断连，属于交付失败；不能通过重新调用模型修复已断开的连接。

跨连接重新取结果需要正式的续取协议和原 logical ID，不在首期悄悄新增后台任务。明确取消后不再启动新生成，既有用量回收继续有界完成。

对已断开的连接不强求补发内部 terminal 或公开终态帧；仅记录取消/交付失败并完成有界内部清算。

## 6. 恢复策略与统一预算

下列是开发初始策略，不是已测得的性能最优参数：

| 项目 | 决策 |
| --- | --- |
| 真实模型调用 | 每 logical request 最多 11 次；同号、切号、会发请求的兼容修复共享 |
| 总时间 | 从入口起 900 秒绝对时限，排队/冷却/重试均计入 |
| 旧 300 秒恢复资格门 | 删除该独立语义；不能用设 0 的方式关闭，因为当前 0 表示默认 300 |
| 首个可用输出 | 每次真实 dispatch 最多 120 秒，继承逻辑剩余期限 |
| 初轮执行与预留 | 初始建议最长 600 秒，并为恢复预留约 300 秒；必须扣除入口已耗时和最终交付余量 |
| 原号瞬时故障 | 初次失败后优先最多两次原号退避尝试；每次重新准入，不绕过冷却 |
| 旧账号级禁同号配置 | 受管 v1 的可恢复瞬时故障覆盖 `pool_mode_retry_count=0` 的旧次数限制，仅在本链路允许最多额外两次；账号 disabled、凭据/安全拒绝和冷却/探针准入仍生效，部署时显式告知运营者 |
| 重试间隔 | 退避与抖动，实际等待不短于 Retry-After/现有账号冷却；不忙轮询 |
| 独立次数捷径 | 首输出只切一次、OAuth 429 累计三次直接结束不再独立终结 logical request |
| 后续恢复轮 | 使用剩余绝对时间，不给每轮重新发放 900 秒或反复扣留 300 秒 |
| 限额正常结束 | Responses 已支持的 max_output_tokens/max_tokens incomplete、Chat length/tool_calls 保留本来语义 |

11 次是最大调用数，不保证每个请求打满。时间不足、已证实没有可行恢复路径可先结束，但停止原因必须真实。只有“当前全部冷却”不能直接冒充永久无账号；应在预算内等待最早可能准入时间。

600/300 是首轮不吃完全部恢复机会的初始工程选择，可能中断原本会更晚成功的生成；上线前按各模型延迟与取消比例验证，不声称已有生产分位依据。

400 参数错误只执行明确模型范围的兼容规则；每种变换去重，模型/权限/格式约束不被任意改写。本次 none/minimal 与模型支持档位的冲突单列工作项，不因“要重试”就隐式更换模型或删上下文。安全/内容策略拒绝不靠换号规避。

## 7. 续聊、别名和可信隔离

### 7.1 原号恢复与历史重建

绑定 previous_response_id 的请求先保留原号恢复，不因 shared budget 存在而禁止同号重试。永久排除与暂时失败/冷却分开；只有确定不可再用的账号才硬排除。

跨号前验证完整输入、前轮成功输出、tool call/result 对应、指令、附件可访问性和 opaque 内容可移植性。复用现有 replay builder 和 bridge 的 AllItems 收集逻辑，但不能把 tool-only replay 或 response→account 路由映射叫作完整历史。

新快照复用既有存储设施，设置 TTL、单记录/父链长度/全局容量上限。旧会话缺历史、链断裂或不可移植时，继续原号有界恢复；不盲删 previous_response_id。

父链完整性与容量门仅阻断跨账号历史重建；仍满足 owner/egress 校验的同账号续聊不因父链超过容量而被拒绝。

### 7.2 可见 logical ID 与真实 winner ID

假设客户端已看到 A，重新生成实际上游成功于 B，下一轮携带 A 时必须在现有 owner/account/egress 校验前，解析可信的 `A → B + winner account/egress` 绑定。仅把 A 重新绑到 B 的账号但仍向上游发送 A 是错误的。

alias 必须是随机不透明标识、按可信 caller 隔离、有时效、不可由终端用户任意指定映射；尚未到达可接受终态或已失败的逻辑响应不能伪装成可续接成功响应；合法 incomplete 限额结束保留真实状态。成功终态对外发送前，原子持久化 alias 对应的实际 ID、账号、出口、历史引用和状态处理策略；同一 alias 不被多个轮次覆盖。读取失败/过期时禁止把代理 alias 原样传给上游。开发文档必须规定响应取回/删除等接口的能力边界。

首期仅承诺后续 `previous_response_id` 解析，不承诺 `GET/DELETE /responses/:id` 取回或删除代理 alias；此能力需另立接口契约。

已发出的账号相关 HTTP 头不能事后替换。alias 记录明确的 turn-state 处理策略，命中 alias 时确定性剥离客户端携带的旧 blob，不依赖进程内 provenance 恰好仍在。保留原始头实际交付的归属事实，不把未交付的 winner 头伪记为已交付。首期默认不主动注入新的票据；若某目标客户端必须依赖 winner 状态，须由其专门兼容门验证既有原生回合机制，否则不能宣称该客户端通过。不恢复主动 STATE 采集、续期或新票据系统。

### 7.3 隔离而非新增用户系统

复用验签后的 NewAPI user/token/origin 与 Sub2 接入 key 建立缓存命名空间；客户端自报 session ID 不是可信身份。现有 NewAPIOrigin 是接收目标 origin，不是独立发行方 ID；本方案针对当前单 NewAPI 部署，不虚称支持多个共享密钥、编号重叠的发行方。

缺少可信归因时关闭新增的跨请求共享历史/alias 能力，同时不得开启依赖 alias 的可见 Responses 重生；保留不改变对外响应身份的既有恢复和现有认证。目标 NewAPI 管理链路必须验证可信归因到位后才能启用新模式。无效签名继续拒绝，不能降级成“未提供”。

## 8. 账单、性能和日志

### 8.1 既有职责

NewAPI 维持其既有用户计费生命周期。内部控制帧和代理生成的重生提示不参与模型 token 估算；失败轮的暂态 usage 与工具次数不能污染最终轮统计。展示转录、winner 的恢复历史、winner 的计量三者分离；不能用最终公开 output 的全部文本估算最终轮成本。Sub2 的上游尝试费用只作运营观测，未知成本记录为未知，不伪装成零，不新增终端收费体系。最终失败的结算继续遵循 NewAPI 已有规则，本项目不借恢复重写其收费政策。

winner-only 计量覆盖原生 Responses/Chat、双向流转换及 SSE→JSON 聚合。对外展示的转换状态保持连续，缺上游 usage 时另按 attempt 统计 winner 文本；内部 terminal 以明确的 Chat/Responses 用量格式标记及完整原生快照传递，显式零值不能被旧轮非零值覆盖。

### 8.2 性能原则

- 不因恢复能力给正常文本增加“等待整轮完成”的门槛。
- 不在每个 chunk 或首文本热路径新增远程同步依赖；成功终态前必须完成的 alias 原子持久化和历史一致性提交属于明确例外，其失败语义与耗时在开发文档定义并测量。
- 只做必要的增量映射、局部单元暂存和有界已交付转录记录；需要磁盘时保证配额、清理和取消收尾。
- 分别测量首个真实文本、首次工具可执行时间、无故障总耗时、恢复成功耗时、CPU/内存/I/O 和取消率。提示和心跳不计作模型 TTFT。
- 调度/兼容参数必须有小范围真实客户端验收；没有测量结果时不承诺“性能无影响”或给出虚构百分比。

### 8.3 必需观测

沿用现有 request ID/ops attempted events，增加：logical ID、attempt 编号、账号、恢复动作、失败阶段、是否已公开文本、已提交工具边界、剩余调用/时间、冷却等待、历史完整性、最终 stop_reason、交付状态。

`switch_count` 不等于实际模型调用数；失败 attempt、最终失败请求、成功恢复请求分别统计。不再只用笼统 exhausted 掩盖“绑定账号选不出”“计时门提前关闭”等不同原因。日志不含 prompt、参数正文、密文或凭据。

## 9. 实施次序与完成门槛

1. **统一恢复编排**：两种 HTTP 入口接入同一逻辑预算；上下文分层；原号恢复、暂时排除和冷却；取消旧提前终结语义。
2. **真流式可见重生**：逻辑输出器、Responses/Chat 分段和唯一终态；内部控制与 NewAPI accumulator 协作；工具/结构单元单独保护。仅完成第一步不能宣称已解决输出后失败。
3. **续聊与别名**：winner alias、turn-state 隔离、完整快照与跨号重建；遗留历史缺失的原号恢复路径。
4. **协议与性能验收**：按实际 SDK/客户端及转换链路验收；通过后依既有手册分阶段发布。原生 WS 和其他入口另列能力，不自动继承 HTTP 完成声明。

必须覆盖以下回归：

- 绑定账号首次 500 后同号第二次成功；同号耗尽后有历史切号成功。
- 输出文本后 429/HTTP2/overload，用户看到明确标记与新答案，连接未被中间 failed 终结。
- reasoning 后超时、半段工具参数后断流，实际启动下一尝试且工具不重复执行。
- 三次 429、两次首输出超时、超过 300 秒后的首次错误均不被特殊门提前停止。
- 客户端增量读取与最终聚合结果一致；Responses IDs/index/sequence、Chat choice/终态正确。
- 下一轮 previous_response_id 使用 logical alias 时能到真实 winner；跨用户/伪造/过期均拒绝越权。
- JSON/schema 不被重启提示污染；完整 JSON 生成后、终态前失败仍只交付一个合法结构结果；合法限额结束不被错误重试，截断工具参数不被执行。
- 单轮期限、逻辑期限、用户取消、磁盘/容量故障、冷却等待与并发预算无死锁/泄漏。
- NewAPI 中间控制不计正文/usage；一条逻辑请求只发生一次终态处理。
- 正常文本首字没有整轮等待；工具/结构延迟和映射开销有真实测量。

**发布阻断**：目标客户端不能正确处理可见重生、alias/turn-state 未闭环、工具可能重复执行、结构格式损坏、恢复预算可被重置、资源无界，任何一项未解决都不能宣布该入口完成。不得以重新启用整段普通文本缓存、伪造完成、提前抛错或静默改变格式来规避。
